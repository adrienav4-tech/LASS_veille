Qu'est-ce que le paradigme LASS ?

Le Language-Augmented Audio Source Separation (LASS) représente une rupture paradigmatique dans le traitement du signal audio. Là où la séparation aveugle de sources (BSS) tentait d'isoler tous les composants d'un mélange sans connaissance préalable, le LASS introduit une intention linguistique comme signal de guidage.

En termes concrets : au lieu de demander à un modèle de "tout séparer", on lui dit "extrais uniquement les sirènes de police" ou "isole la guitare acoustique de ce mix". Cette requête en langage naturel oriente le modèle vers une cible précise au sein du mélange.

Définition formelle. Soit un mélange audio x = s₁ + s₂ + ... + sₙ et une requête textuelle q décrivant une source cible sₜ. Un modèle LASS apprend la fonction f(x, q) → ŝₜ telle que ŝₜ ≈ sₜ.

Figure 1. Pipeline général d'un système LASS. L'encodeur audio produit une représentation du mélange, l'encodeur de texte (CLAP/BERT) encode la requête. Le réseau de séparation utilise le vecteur textuel pour conditionner un masque appliqué au spectrogramme.

L'espace latent commun texte-audio

Le mécanisme central du LASS repose sur un alignement multimodal : encoder le texte et l'audio dans un même espace vectoriel, de sorte que "guitare acoustique" et le son d'une guitare acoustique soient proches dans cet espace. C'est exactement ce que font les modèles de type CLAP (Contrastive Language-Audio Pretraining).

Figure 2. Apprentissage contrastif CLAP. Les paires (audio, description textuelle) sont rapprochées dans l'espace latent (perte InfoNCE), tandis que les paires non correspondantes sont éloignées. La proximité cosinus entre z_t et zₐ permet ensuite de guider la séparation.

Architectures principales

Deux familles d'architectures dominent la littérature LASS :

U-Net conditionnel

Inspiré de la segmentation d'image, le U-Net audio opère sur le spectrogramme log-mel. L'encodeur compresse le signal en une représentation latente ; le décodeur reconstruit le spectrogramme de la source cible. Le conditionnement textuel se fait via FiLM (Feature-wise Linear Modulation) ou cross-attention à chaque niveau de l'encodeur.

Transformer séquentiel

Des modèles comme AudioSep utilisent un Transformer (ResUNet + QueryNet) où la requête textuelle sert de token de conditionnement dans les blocs d'attention. Cela permet une modélisation plus fine des dépendances à longue distance dans le signal audio.

Figure 3. U-Net conditionnel pour LASS. L'encodeur extrait des features multi-échelles du spectrogramme ; le vecteur textuel z_text injecte son information via FiLM ou cross-attention. Les skip connections transmettent les features haute résolution au décodeur, qui produit un masque temps-fréquence.

Métriques d'évaluation

Les modèles LASS sont évalués sur des benchmarks comme MUSDB18 (musique), ESC-50 (sons environnementaux), FSDSounBank et AudioCaps. Les métriques principales sont le SDR (Signal-to-Distortion Ratio), le SI-SDR (Scale-Invariant SDR), et le PESQ (Perceptual Evaluation of Speech Quality) pour la parole.

Figure 4. Les trois métriques principales pour évaluer la qualité de la source séparée. Un modèle LASS performant vise >15 dB de SDR sur MUSDB18 et >3.5 de PESQ sur les tâches de parole.

Défis ouverts

Généralisation out-of-distribution. Les modèles LASS peinent à séparer des sons non vus à l'entraînement, notamment lorsque la requête textuelle décrit un concept abstrait ("le son de la peur") plutôt qu'une classe sonore précise.

Polysémie textuelle. La même description peut couvrir des sons très différents selon le contexte. "Basse" peut désigner un instrument ou une fréquence. L'ambiguïté linguistique reste un problème ouvert dans le conditionnement textuel.

Séparation multi-cibles. La plupart des modèles actuels sont mono-requête. Séparer simultanément plusieurs sources décrites par des requêtes différentes (ex. "la guitare ET le chant") reste un challenge architectural.

Le Processus de veille

Cette page est mise à jour automatiquement chaque jour à 6h00 UTC via GitHub Actions. Le pipeline agrège des publications depuis quatre sources scientifiques, filtre par mots-clés thématiques, déduplique et publie sur GitHub Pages. Aucun serveur externe, aucune base de données payante.

Sources agrégées

📄
arXiv
Preprints · API officielle
API REST export.arxiv.org. Requêtes sur les catégories cs.SD (Sound), eess.AS (Audio), cs.CL (NLP). Retourne titres, auteurs, résumés, PDF. Quota gratuit illimité.
🎓
Google Scholar
Publications académiques · SerpAPI / scholarly
Via la librairie Python scholarly (scraping) ou SerpAPI (payant, plus fiable). Accès aux citations, indices h, revues peer-reviewed absentes d'arXiv (IEEE, ACM, ISCA/Interspeech).
🔬
Semantic Scholar
Graph sémantique · API officielle gratuite
API REST officielle api.semanticscholar.org. Fournit en plus des citations croisées, l'influence académique (influential citations) et des recommandations basées sur le graphe de citations. Clé API gratuite, 100 req/5min.
⚡
IEEE Xplore
Conférences & revues · API officielle
API ieeexplore.ieee.org/rest/search. Indispensable pour couvrir ICASSP, ICLR, Interspeech, WASPAA — les conférences majeures du traitement du signal audio. Clé API gratuite (200 req/jour).

Pipeline technique complet

01
Déclenchement — GitHub Actions cron: 0 6 * * *
Le workflow YAML se déclenche chaque jour à 6h00 UTC. Il provisionne un runner Ubuntu, installe Python 3.11 et les dépendances (requirements.txt).
02
Scraping multi-sources fetch_papers.py
Le script interroge en parallèle : arXiv API, Semantic Scholar API, IEEE Xplore API et Google Scholar (via scholarly). Pour chaque source, les requêtes combinent les termes des groupes A+B et A+C. Les résultats bruts sont mis en file.
03
Filtrage & scoring filter.py
Chaque article reçoit un score de pertinence basé sur la présence de mots-clés dans le titre (×3) et le résumé (×1). Seuls les articles avec un score ≥ 2 sont retenus. Les doublons (même DOI ou titre similaire à 90%) sont supprimés.
04
Génération JSON data/lass_papers.json
Les 25 meilleurs articles (par score × récence) sont sérialisés en JSON avec les champs : title, authors, date, summary, url, source, tags. Le fichier est committé directement dans le repo.
05
Commit & déploiement gh-pages
Le bot GitHub Actions commit le JSON mis à jour. GitHub Pages redéploie automatiquement. La page est accessible en quelques secondes après le commit. Le last-update est inscrit dans le JSON.
